[[ch-security-controls]]
= Security Controls: What Is Enforced and What Is Planned

_Module: `gcu-taskgraph` (the actor remoting controls are in gcu-actors, the cluster controls in gcu-cluster). See <<ch-modules>>._

The library runs things on behalf of a flow definition: scripts, rule expressions, HTTP calls,
file operations, messages from other processes. This chapter is the single place that says,
for each of those, what limits it today, what the agreed design is, and which release brings
the two together. It is updated with every release that changes a control, so it can be
read as the current state of the hardening work.

Read this chapter before deciding how much to trust a flow you did not write yourself.

== The Trust Model

The controls are designed for one situation: flows are written by people who are trusted,
but a flow can contain text that came from somewhere else. A URL, a file path, a rule
condition or a script body may have been copied, generated, or steered by content read from
an outside source. The controls limit what such text can reach.

They are a *reduction*, not isolation. Everything in a flow runs inside one JVM under one
operating-system user. A control that refuses a file path or a class name narrows what
mistaken or steered text can do; it does not contain code written by someone who is trying
to get out. Flows supplied by an untrusted party need a separate process with its own
operating-system limits, which is outside what this library provides.

== One Vocabulary: Restricted, Capabilities, Trusted

The agreed design uses the same three levels everywhere, so that a flow states its needs in
one way.

[cols="1,3",options="header"]
|===
| Level | Meaning

| Restricted
| The default. The task can compute on the data it was given and nothing else.

| Restricted plus capabilities
| The flow names what it needs: `allow 'files'`, `allow 'http'`, `allow 'sql'`,
`allow 'process'`. Each capability is bounded by the control for that area, described below.

| Trusted
| `trusted true` on a task removes the restriction for that task, and is logged. It is a
deliberate statement in the flow, visible to a reviewer.
|===

Version {gcu-version} implements all three levels for `ControlTask` rule conditions and
`ScriptTask` scripts, with all four capabilities, and the `ShellTask` that `allow 'process'`
turns on (1.4.1). The sections below say what each area does now.

what changes.

== Scripts and Rule Conditions

*Rule conditions, from 1.4.0.* A `ControlTask` `when:` string is one expression over `input`
(the upstream result), `globals` (a read-only copy of the graph's globals) and `memory`.
It may use:

* literals, list and map literals, and strings with `${}` values;
* `+== != === !== < <= > >= <=>+`, `&& || !`, `+ - * / % **`, `in` and `!in`, the match
  operators `==~` and `=~`, the conditional operator and the Elvis operator;
* property and index access, with `?.`;
* the methods `size`, `isEmpty`, `contains`, `containsKey`, `startsWith`, `endsWith`,
  `matches`, `toString`, `toLowerCase`, `toUpperCase` and `trim`, and the functions and
  constants of `Math`;
* a cast or `as` to a number type, `String` or `Boolean`.

Inside that list an expression means what it means in Groovy. A property of a map is the
entry of that name; a property of an object is its getter, public field or
`propertyMissing`; a property of a list is the list's own (`empty`, `first`, `last`) or else
that property of each element; indexes may be negative; `?.` stops at a null; truth, number
arithmetic across types, comparison with `null`, and `in` on a list, array, map or text all
follow Groovy 6. A test holds the rule profile and Groovy side by side on
some two hundred expressions and requires the same value, or a failure in both.

Where the profile differs it refuses: `-`, `*` and `/` take numbers only (`text * count` is
allowed); a list is not indexed by a range; `globals` is a plain map, so the binding's own
getters such as `globals.keys` are not there.

Nothing else: no object creation, imports, closures, loops, assignments, definitions or any
other method.

How it is enforced:

* The condition is parsed and checked against that list when the graph is validated
  (`TaskGraph.validate()`, which `start()` calls). A condition that does not parse, names
  something it is not given, or uses anything outside the list stops the graph before any
  task runs. Every bad rule is named in the one error.
* A condition is never compiled to a class or run as a script. GCU walks the checked
  expression itself, so each property read, index and method call is checked again against
  the object actually reached. `class`, `metaClass`, `classLoader`, `properties` and their
  relatives are refused by name. Classes, class loaders, reflection objects, files, paths,
  URLs, processes, threads, closures, anything closeable and the graph's own context are
  refused by type. A refusal is a `SecurityException` and fails the node.
* A property of a map is the entry of that name, never a method of the map.
* A condition that throws fails the node. Before 1.4.0 it was read as false, and the next
  rule or the default applied.
* A rule is parsed once and the result reused by every task and run. A failed `ControlTask`
  is not retried: the same input gives the same failure. Its `TASK_FAILED` event says so:
  `metadata.notRetriedBecause` is `not-retriable` and `isPermanentFailure()` is true, so
  whatever drives the graph can tell not to run it again unchanged.
* `trusted true` on the task evaluates its conditions as unrestricted Groovy against the
  live globals, as every `ControlTask` did before 1.4.0. It logs a warning each run.

What it does not do. It is a reduction inside one JVM, not isolation:

* A rule can call the getters and `toString()` of the objects it is handed. Do not put an
  object whose getters have side effects where a rule can reach it.
* A pattern given to `matches`, `==~` or `=~` can be slow on hostile text, and a rule has
  no timeout of its own.
* The by-type list is a deny-list. An object of a type not on it is readable.

*Scripts, from 1.4.0.* A `ScriptTask` script is restricted unless its task says
`trusted true`. A restricted Groovy script is a statement language: variables, conditionals,
loops, closures, its own methods, `@Field`, and the collection, text, number and date
methods of Groovy and Java, with these classes available by name:

[cols="1,3",options="header"]
|===
| Area | Available to a restricted script

| Core Java
| `java.lang` value types, `Math`, `StringBuilder`, the common exceptions (to throw and to
catch; not `Throwable` or `Error`), and of `System` only the clock; `java.util` with
`function`, `stream` and `regex` (less `Formatter`, `Scanner`, `Timer`, `ServiceLoader` and
`ResourceBundle`); `java.time`; `java.math`; `java.text`; `java.nio.charset`

| Concurrency data types
| `java.util.concurrent` collections, `TimeUnit`, `atomic`. No threads or executors.

| Encoding and identity
| `UUID`, `Base64`, `URI`, `URLEncoder`, `URLDecoder`, `MessageDigest`

| Groovy
| `groovy.json`, `groovy.xml`, `groovy.yaml` (their `parseText`, not `parse`); closures,
ranges, tuples, `Expando`; the `@Field` annotation and no other

| This library
| `Promise`, `Promises`, `Gstream`
|===

How it is enforced:

* *When the graph is validated.* The script is compiled, and the graph refused with the task
  named, if the script:
** names a class outside the table. `File`, `URL`, `Thread`, `ProcessBuilder`, `Class`,
   `GroovyShell` and `Eval` cannot be written at all: not in a `new`, a cast, a declaration,
   a `catch` or an import;
** defines a class, or uses a static import, an import alias, or any annotation but
   `@Field`. Annotations are checked before the compiler acts on any of them, so `@Grab`
   and `@ASTTest` never run;
** uses, on anything, one of the names in the profile's deny lists: `getClass`,
   `metaClass`, `invokeMethod`, `evaluate`, `binding`, `with`, `tap`, `use`, `execute`,
   `toURL` and their relatives;
** computes a method or property name, or uses a method pointer, `.@`, `super` or
   `synchronized`;
** uses a class for anything but its public static members: `String.format` yes,
   `String.classLoader` no.
* *While the script runs.* The compiler wraps the receiver of every method call, property
  read or write, index and `<<`, and whatever is iterated, spread or cast, in a check of the
  object actually reached. Text, numbers, collections, maps, closures and instances of the
  classes in the table pass. A class held as a value, a class loader, a reflection object, a
  file, path, URL, process, thread or anything closeable is refused with a
  `SecurityException`, however the script came by it. A `File` in the bindings can be passed
  on, but not read, written, listed or iterated.
* *Groovy's meaning is kept.* The check returns the receiver and Groovy still makes the
  call, so a script inside the profile does what the same Groovy does. A test runs some
  seventy-five scripts both ways and compares the results.
* *The context.* `ctx` and `context` are a read-only view: `ctx.globals` (a copy that cannot
  be changed), `ctx.get(name)` and `ctx.taskId`. No credentials, pool or graph.
* *Each run* gets a new script instance and a new binding. The script is compiled once per
  task.
* *`scriptTimeout` is enforced.* The script runs on its own thread; when the time is up the
  task fails with a `TimeoutException` and that thread is interrupted. A restricted script
  checks for interruption on every loop pass, method and closure, and so stops.
* *A refusal is not retried*, and the failure is marked permanent
  (`TaskFailureSignal.isPermanent`).
* *`customScriptBaseClass` still works.* The base class's public methods are callable from
  the script by name. The script is still compiled under the profile.

Capabilities (level 2) are granted per graph:

* `allow 'files'` binds `files`: `read`, `readLines`, `write`, `append`, `exists`, `size`
  and `list`, on text, under the rules of an unconfigured `FileTask`: inside the graph's
  working directory and its `allowedDirectories`, no symbolic links, the size limits.
* `allow 'http'` binds `http`: `get`, `post`, `put` and `delete`, each returning `status`,
  `body` and `headers`. Every address goes through the `HttpTask` guard, a local service
  needs `allowLocal`, and a redirect is returned, not followed.
* `allow 'sql'` (1.4.1) binds `sql`: `query`, `queryForMap`, `queryForObject` and `update`
  on the datasources the graph declares. See <<script-sql>>.
* `allow 'process'` (1.4.1) binds `process`: `shell(interpreter, script, args)`, with the
  checks of a `ShellTask`. See <<shell-commands>>. It is not called `run`: a restricted
  script may not call `run()`, which would run the script itself again.

A script reaches a capability only through the methods listed (1.4.1). Groovy lets a caller
read a private field through property syntax and call a private method by name, so before
1.4.1 a script could reach what a capability holds: it could add a local service to the
list `http` checks against and then call it, or raise the size limit of `files`. Now any
property, index or operator on a capability, and any method it does not list, is a
`SecurityException`.

`trusted true` (level 3) compiles the script as plain Groovy and hands it the `TaskContext`
itself, as every script had before 1.4.0, and logs a warning each run. `sandboxed false` is
the old spelling of the same thing. It no longer reads the `ENVIRONMENT` variable.

Other languages. JavaScript runs on Nashorn started with no Java access and a class filter
that exposes nothing, in a new engine for every run. Any other JSR-223 language runs only
with `trusted true`; without it the graph fails validation. A JavaScript loop cannot be
interrupted: on timeout the task fails and the run is abandoned.

What it does not do. It is a reduction inside one JVM, not isolation:

* A script can call any public method of an object the flow puts in its bindings, and can
  pass any object it holds to a method it is allowed to call. Bind data, or objects you
  would let the script drive.
* Beyond the table the by-type list is a deny-list. An object of a type on neither list can
  be used.
* There is no memory limit. A script can build a very large collection.
* Work a script starts elsewhere (`Promises`, a parallel stream) is not stopped by its
  timeout, and a slow regular expression is not interrupted.
* `with`, `tap` and `use` are refused, and an object's properties cannot be read by index:
  write `order.total`, not `order['total']`. Maps and lists index as usual.
* `println` writes to standard output. In a process that speaks a protocol there, use `log`.

[[shell-commands]]
== Shell Commands

*From 1.4.1.* A `ShellTask` runs a PowerShell, cmd, bash or Python script as a separate
process, which cannot touch the graph or the context in memory. A restricted script reaches
the same thing through `process.shell(...)`, with the same checks. Both are off unless the
graph says:

[source,groovy]
----
allow 'process'
interpreters 'powershell', 'python'
----

`allow 'process'` alone runs nothing. The checks, all made before any process starts and,
where they can be, when the graph is validated:

[cols="1,3",options="header"]
|===
| Control | What it does

| Interpreters
| Only those the graph names. `interpreterPath 'python', '...'` picks the executable.

| The script
| Goes to the interpreter by a temporary file in a directory of its own (PowerShell, cmd) or
by standard input (bash, Python), never on the command line. Standard input is closed once
the script is written, and interpreters start non-interactive and without profiles.

| Arguments
| Passed as a list, with no shell in between: `;`, `{vbar}`, `$(...)` arrive as text. On Windows
a double quote or a line break is refused for every interpreter, and cmd and bash take only
letters, digits and `_ . , : / = + @ -` (cmd also `\`), because cmd and the WSL bash
launcher read their command line again as a shell would.

| Working directory
| The graph's `workingDirectory`, or one inside it and its `allowedDirectories`.

| Environment
| Rebuilt for each run: the few variables an interpreter needs to start (on Windows
`SystemRoot`, `PATH`, `TEMP`, `USERPROFILE` and their like; nothing naming the user or the
machine), those the graph names with `passEnvironment`, and those the task sets with `env`.

| Time
| `processTimeout`, 60 seconds by default. At the limit the process and every process it
started are stopped, and the task fails with a `TimeoutException`. The same when the task
is cancelled. From 1.4.2, on Windows, each run is held in a Job Object, so this includes
processes whose parent has already exited (Git Bash starts every command of a script that
way, through a stub that exits at once). Nothing a run starts outlives it: when the
script finishes, a background process it left running is stopped too, and if this JVM
dies during a run, Windows ends the run's processes with it. A task that means to leave a
process running says `keepBackground true`: it is then kept until the graph ends, its
ids are in the result's `keptProcessIds` and the audit record, and a timeout or a failed
script still stops it. Elsewhere, or when the JDK
refuses native access, a timeout reaches the processes still linked to the run by their
parents, and a finished script's background processes are left running. The JDK warns once about
native access unless the JVM starts with `--enable-native-access=ALL-UNNAMED`.

| Output
| stdout kept up to `maxOutput` (1 MB), stderr up to `maxErrorOutput` (64 KB); the rest is
read and dropped, and the result says `stdoutTruncated` or `stderrTruncated`.

| Tripwires
| Refused before running: for PowerShell `Remove-Item` and its aliases, `Clear-Content`,
`Stop-Computer`, `Stop-Process`, `Format-Volume`, `Invoke-Expression`/`iex`,
`Set-ExecutionPolicy`; for cmd `del`, `rd`, `format`, `shutdown`, `reg delete`, `taskkill`
and their like; for bash `rm`, `chmod`, `kill`, `shutdown`, `mkfs`, `dd of=`, a fork bomb,
a download piped to a shell; for Python `shutil.rmtree`, the `os` delete and exec calls,
`subprocess`, `ctypes`. A check against mistakes and steered content, not a boundary.

| Elevation
| `sudo`, `doas`, `runas`, `su`, `-Verb RunAs` are refused, trusted or not.

| Exit code
| A non-zero exit fails a `ShellTask` as an ordinary failure, so its retry policy applies.
`process.shell` returns the code for the script to read.

| Audit
| Each run is logged on `org.softwood.dag.audit` and passed to `TaskContext.auditListener`
if set: task, interpreter, working directory, SHA-256 of the script, argument count, exit
code, duration, truncation, trusted, timed out.
|===

A refusal is a `SecurityException`, fails the graph's validation where it can be known then,
and is never retried.

`trusted true` on a `ShellTask` skips the interpreter list and the tripwires. It does not
skip `allow 'process'`, the working directory, the environment, elevation, the timeout or
the output caps, and it is logged each run.

A flow can run its shells somewhere else with `shellRunner` on the graph or `runner` on the
task (a `ShellRunner`). The checks above run before any runner sees the request. The
agentic-workflow server is to plug in one that hands the command to the filesystem server's
`execute`, so the platform keeps one guard.

The process runs as the same operating-system user as the JVM. The directory list and that
user's own rights are the real limit.

[[script-sql]]
== Database Access from Scripts

*From 1.4.1.* The flow author declares a datasource by name, and `allow 'sql'` gives a
restricted script `sql` to use it:

[source,groovy]
----
allow 'sql'
datasource 'orders', ordersProvider                       // an SqlProvider: read-only
datasource 'audit', auditProvider, writable: true, maxRows: 500

scriptTask('report') {
    script '''
        def rows = sql.query('orders', 'select name, qty from orders where qty > ?', [2])
        rows.collect { it.name }
    '''
}
----

* A script names a datasource; it never supplies a URL, a driver or a provider, and it
  cannot reach the provider, a connection or the list of datasources.
* One statement per call. Quoted text and comments are skipped when looking for a second;
  where a database could read the text differently the check sees more code, not less.
* A query starts with `SELECT` or `WITH` and has no write word anywhere in its code
  (`INSERT`, `UPDATE`, `DELETE`, `MERGE`, `INTO`, schema changes, procedure calls). That
  matters: a database can delete inside a query (H2's `old table (delete ...)`, a Postgres
  `WITH ... DELETE`).
* `update` needs `writable: true` on the datasource and takes `INSERT`, `UPDATE`, `DELETE` or
  `MERGE`, never a schema change, a grant or a procedure call.
* A query that returns more than `maxRows` rows (10,000 by default) fails. The rows are
  fetched before they are counted: the cap limits what the script gets, not what the
  database reads.
* Each call is logged and passed to the audit listener: datasource, operation, SHA-256 of
  the statement, rows.
* A refusal is a `SecurityException` and is not retried.
* There is no query timeout of its own: `scriptTimeout` abandons a long call; it does not
  cancel it on the database.

The statement check reads text, not a database's grammar. Back a read-only datasource with a
database account that cannot write: that is the real control. The flow owns each provider and
closes it; the graph does not.

== HTTP Calls

*Enforced from 1.3.0.* Before 1.3.0 `HttpTask` called whatever URL it was given and followed
redirects wherever they led, `localhost` and private networks included. It now checks where a
request is going before it sends it.

[cols="2,3",options="header"]
|===
| Destination | Default

| Public internet, HTTP or HTTPS
| Allowed.

| Private network addresses
| Blocked.

| `localhost` and loopback
| Blocked unless the flow names the host and port, on the task or once for the graph.

| Cloud metadata addresses
| Always blocked.
|===

[source,groovy]
----
TaskGraph.build {
    allowLocal 'localhost:8082'              // once for the graph

    httpTask('lookup') {
        allowLocal 'localhost:8084'          // or on the task
        url 'http://localhost:8084/items'
    }
}
----

The URL is checked before the request: its scheme, then every address its host resolves to.
Redirects are followed one step at a time, each checked against the same rules, up to five;
a sixth fails the task. A redirect that leaves the origin the flow named is followed without
the task's credentials: its `auth` settings and any `Authorization` or `Cookie` header stay
behind. A redirect from HTTPS to HTTP is not followed.

`allowLocal` takes `host:port`. An entry naming any loopback name covers the others on the
same port, so `localhost:8082` also admits `127.0.0.1:8082`. It does not open private network
addresses, and it never opens a cloud metadata address. A flow that has to call a host on a
private network marks the task `trusted true`, which turns the guard off for that task and
is logged each time it runs. `securityConfig` on the task replaces the standard policy with
one of your own: a host allow-list, HTTPS only, a different redirect limit.

One limit to know. The addresses checked are the ones the JVM resolved a moment before the
connection and holds in its address cache, which the connection then uses. The check is not
made on the socket itself. It holds as long as the JVM's address cache is on, which it is by
default; do not run with `networkaddress.cache.ttl=0`.

== File Operations

*Enforced from 1.3.0.* A `FileTask` with no security configuration runs under the strict
configuration, confined to the graph's working directory, or the JVM's working directory if
the graph names none. The strict limits apply: symbolic links are not followed, 100 MB per
file, 1 GB and 10,000 files per operation, and a recursion depth of 50. A file outside the
scope fails the task with `SecurityException`.

Reaching outside the working directory takes one line naming the directories:

[source,groovy]
----
TaskGraph.build {
    workingDirectory '/var/app/run-42'       // the default scope for this graph
    allowedDirectories '/var/app/data'       // more, for every FileTask in the graph

    fileTask('collect') {
        allowedDirectories '/var/app/incoming'   // more, for this task
        sources { directory('/var/app/incoming') { pattern '*.csv' } }
    }
}
----

A named directory has to exist when the task runs. A task given its own `securityConfig`
runs under that and nothing else. The permissive configuration remains but has to be asked
for by name: `securityConfig FileTaskSecurityConfig.permissive()`, or `trusted true` on the
task, which is logged. `permissive()` no longer consults the `ENVIRONMENT` variable; before
1.3.0 it refused when that said production, while an unconfigured task was handed the
permissive configuration all the same.

== Remote Actor Transports

*Enforced from 1.3.0.* Before 1.3.0 a transport started as a server accepted connections on
every network interface, with authentication off unless configured, and delivered to any
actor in the system by name.

A server transport now listens on `127.0.0.1` unless given another address. Listening on any
other address with authentication off is refused when the transport starts, with a message
naming the two ways forward: pass an `AuthConfig` with `enabled` true, or set `insecure` on
the transport to say that an open listener is intended. Without TLS on a wider address the
transport starts and warns.

[source,groovy]
----
def transport = new RSocketTransport(system, 7000, true, tlsConfig, authConfig)
transport.bindAddress = '10.0.0.10'      // default 127.0.0.1
transport.start()
----

Only an actor marked remote can be reached from outside. Mark it in its builder with
`remote true`, or afterwards with `system.markRemote('name')`. A message for any other actor
is answered exactly as a message for a name that does not exist, so a caller cannot tell an
internal actor from a missing one. The HTTP server's worker pool is bounded.

== Cluster

*Today (from 1.2.1).* Pass a `HazelcastSecurityConfig` to `HazelcastManager.initialize`. It
is validated and applied: no multicast discovery, a fixed member list, a bind address and a
fixed port. With multicast disabled and no members named, start-up is refused; nothing falls
back to multicast.

Encryption between members and member authentication are features of Hazelcast Enterprise.
The library uses the open-source edition, which will not start with either enabled. On the
open-source edition, therefore, anything on the same network that knows the cluster name and
can reach the port could join, and traffic between members is not encrypted. Run a cluster
only on a network you control. Calling `initialize` without a security configuration applies
none of the above.

*Added in 1.3.0*, on the open-source edition:

* *Signed task events.* With `messageSigningEnabled` and a `messageSigningKey` in the security
  configuration, every task event TaskGraph publishes is signed. A receiver that listens
  through `HazelcastManager.addTaskEventListener` is given only events whose signature
  verifies; an unsigned or altered event is dropped and logged. Before 1.3.0 the signing code
  existed and nothing called it. The library itself has no listener on the topic: reading it
  directly bypasses the check, so use the manager's method.
* *A deserialisation allow-list.* With a security configuration, Java deserialisation inside
  the cluster is limited to the library's cluster classes, Hazelcast's defaults (`java`,
  `com.hazelcast.`) and the prefixes named in `serializationAllowedPrefixes`. An application
  whose task results travel through the cluster as its own classes names their packages
  there. The filter does not cover the handshake by which a member joins.
* *A warning on an unsecured start.* `initialize` with one argument logs that the cluster has
  no security settings.

What signing covers is the task event topic. The shared maps (graph state, task state, the
actor registry) and actor lifecycle events are not signed: a member that has joined can
write to them. Membership is the control for those, which is the next paragraph.

To get encryption and control over who can join without Enterprise, run the members over
an encrypted private network, such as a VPN or a mesh network, and bind the cluster to that
network's address. The cluster then inherits the network's encryption and membership.

== Java Deserialisation

*Enforced from 1.2.1.* `JavaSerializer` reads through an allow-list. By default it accepts
JDK value types and Groovy's interpolated string, and refuses everything else. An
application that sends its own message classes names their packages when it creates the
serializer. Graph depth, reference count and array length are capped.

== Configuration Files

A Groovy configuration file is a script, and loading it runs it. That applies to
`config.groovy` on the classpath and to every external location the loader reads: files
named by the `app.config` system property or the `externalFiles` option, and directories
named by `app.configDir` or `externalDirs`. Anyone who can write to one of those locations,
or set those system properties, can run code in the process at start-up. Give them the same
protection as the application's own code. YAML, JSON and properties files carry data only.

== Task Results in Logs, Events and Persistence

*Opt-in from 1.2.2.* A task's result can hold what the flow fetched: a token, a customer
record, the body of a document. By default the library writes results as they are, to its
debug log lines, to a persisted snapshot when persistence is on, and to the events it hands
to listeners.

Setting `resultRedactor` on the graph's `TaskContext` puts one function in front of the first
two and adds a redacted copy to the third. The closure receives the task id and the value and
returns what may be shown. `TaskEvent.result` is never altered, so code that reads a result
from an event keeps working; `TaskEvent.redactedResult` is the form to store. A redactor that
throws hides the value. <<tg-06>> has the detail and an example.

The limits are worth knowing. The redactor covers what the library writes. It does not cover
what a task's own code logs, `ctx.globals`, or the value handed from one task to the next,
which has to be real for the flow to work. Exception messages are not passed through it.

== Using the Library Safely at Version {gcu-version}

. Keep script bodies and rule conditions fixed in the flow, and pass outside values in as
  data, even now that both are restricted. Keep `trusted true` for scripts you wrote.
. Name the directories a `FileTask` needs; do not reach for `trusted true` to get past the
  default scope.
. Name local services with `allowLocal`; keep `trusted true` on an `HttpTask` for hosts on a
  network you control.
. Grant `allow 'process'` only to graphs that run shells, name only the interpreters they
  use, and keep `trusted true` on a `ShellTask` for scripts you wrote. Pass variables with
  `passEnvironment` by name.
. Declare a datasource writable only when a script must write, and give each datasource its
  own database account with the rights it needs.
. Mark as `remote` only the actors other processes need. Give a transport on a wider
  address both authentication and TLS.
. Pass a `HazelcastSecurityConfig` with message signing when clustering, listen for task
  events through `addTaskEventListener`, and run the cluster on a network you control.
. Name your message packages when using `JavaSerializer`; prefer JSON or MessagePack.
. Protect configuration locations as you protect code.
. Where results can hold secrets or personal data, set a `resultRedactor` and store
  `redactedResult` from events, not `result`.

For the controls inside the TaskGraph engine itself, validation, guarded task state,
cancellation and timeouts, see <<tg-16>>, and for the task-level security settings as they
are today, <<tg-09>>.
