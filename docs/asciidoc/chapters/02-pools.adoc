[[ch-pools]]
= Pools: Where Work Runs

Package `org.softwood.pool`. Every other capability in the library runs its work on a pool:
promises complete on one, dataflow tasks are launched on one, actors and agents drain their
mailboxes on one, and TaskGraph runs every task on one. This chapter describes the single
pool contract they all share and the one implementation behind it.

== The Contract: `ExecutorPool`

`ExecutorPool` is the only pool interface in the library. Code that needs to run work takes
an `ExecutorPool`, which is what makes it possible to inject a pool in a test or share one
across capabilities.

[cols="2,3",options="header"]
|===
| Method | Purpose

| `execute(Closure)`, `execute(Closure, Object[])`, `execute(Callable)`, `execute(Runnable)`
| Submit work. Returns a `CompletableFuture` for the result.

| `tryExecute(Closure)`
| Submit work without throwing. Returns `false` if the pool is closed or the executor rejects the task.

| `executeWithTimeout(Closure \| Callable, long, TimeUnit)`
| Submit work that is cancelled, with interrupt, if it has not finished in time.

| `scheduleExecution(delay, unit, Closure)`
| Run once after a delay. Returns a `ScheduledFuture`.

| `scheduleWithFixedDelay(...)`, `scheduleAtFixedRate(...)`
| Run repeatedly.

| `getExecutor()`, `getScheduledExecutor()`
| The underlying Java executors, for code that needs them directly.

| `getName()`, `isUsingVirtualThreads()`, `isClosed()`, `shutdown()`
| Introspection and lifecycle.
|===

== The Implementation: `ConcurrentPool`

`ConcurrentPool` implements `ExecutorPool` and `AutoCloseable`. It is a thin layer over Java
executors that adds four things: a preference for virtual threads, clear ownership of the
executor it wraps, cancellation that reaches the running task, and optional admission control.

=== Virtual threads first

The default constructor uses one application-wide virtual-thread-per-task executor, created
once in a static initialiser and shared by every default pool in the JVM. If virtual threads
are not available the constructor falls back to a cached platform thread pool for that
instance. Scheduling uses a shared scheduled executor of daemon platform threads sized at a
quarter of the available processors (minimum one), so a JVM can exit cleanly when its user
threads finish.

[source,groovy]
----
def pool    = new ConcurrentPool('orders')     // shared virtual threads
def fixed   = new ConcurrentPool(8)            // 8 platform threads, owned
def wrapped = new ConcurrentPool(myExecutor)   // your executor, not owned
----

`ConcurrentPool.isVirtualThreadsAvailable()` reports which mode the JVM is in, and
`pool.isUsingVirtualThreads()` reports it for one pool.

=== Ownership

A pool shuts down only what it owns. This is the rule that stops one component's `shutdown()`
from taking away threads that unrelated code is using.

[cols="2,1,3",options="header"]
|===
| How the pool was created | Owns the executor | Effect of `shutdown()`

| `new ConcurrentPool()` with virtual threads available
| No
| The pool is marked closed. The shared executor keeps running.

| `new ConcurrentPool()` without virtual threads
| Yes
| The pool is marked closed and its cached thread pool is shut down.

| `new ConcurrentPool(int poolSize)`
| Yes
| The pool is marked closed and its fixed thread pool is shut down.

| `new ConcurrentPool(ExecutorService, ScheduledExecutorService)`
| No
| The pool is marked closed. The supplied executors are left alone.
|===

The shared executors live for the life of the JVM. A shutdown hook drains them on exit, waiting
up to five seconds for each. `ConcurrentPool.shutdownSharedExecutors()` exists for the rare
case, mostly tests, where they must be stopped explicitly.

Once a pool is closed, `execute` and `executeWithTimeout` throw `IllegalStateException` and
`tryExecute` returns `false`. `close()` delegates to `shutdown()`, so a pool can be used in a
try-with-resources block. `shutdownNow()` and `awaitTermination(timeout, unit)` are available
for owned executors.

=== Submitting work

Every `execute` variant goes through one submission path. The task is submitted to the executor
as a `Callable`, and the `Future` that comes back is bridged to the `CompletableFuture` handed
to the caller. The bridge works in both directions: the result or exception of the task
completes the `CompletableFuture`, and cancelling the `CompletableFuture` cancels the underlying
`Future`, so the running task is interrupted and not merely abandoned.

[source,groovy]
----
CompletableFuture total = pool.execute { priceOrder(order) }
total.thenAccept { println "total: $it" }

pool.execute({ a, b -> a + b }, [2, 3] as Object[])
----

`withPool(executor) { ... }` runs one closure with the pool as its delegate, optionally on a
different executor for that call only.

=== Timeouts

`executeWithTimeout` submits the task and schedules a check on the scheduled executor. If the
task is still running when the check fires, the underlying `Future` is cancelled with interrupt
and the returned future completes exceptionally with `TimeoutException`. If the task finishes
first, the timer is cancelled and removed from the scheduler, so nothing is retained for the
rest of the timeout period. Timed-out tasks are counted in the pool metrics.

[source,groovy]
----
pool.executeWithTimeout({ callSlowService() }, 2, TimeUnit.SECONDS)
    .exceptionally { e -> fallbackValue }
----

A task that ignores interruption keeps its thread until it returns. The caller is released at
the timeout either way.

=== Admission control

Virtual threads make it cheap to start a very large number of tasks, which moves the limit
from threads to whatever those tasks consume. `withMaxInFlight(n)` puts a semaphore in front
of submission: once `n` tasks are in flight, the next `execute` call blocks until one
finishes. Zero or a negative number removes the limit.

[source,groovy]
----
def pool = new ConcurrentPool('db-writers').withMaxInFlight(20)
----

A submitting thread that is interrupted while waiting for a permit gets a
`RejectedExecutionException`.

=== Errors and metrics

`withUncaughtExceptionHandler(Consumer<Throwable>)` registers a handler that is called whenever
a task completes exceptionally. The exception still reaches the task's future; the handler is
for logging and alerting.

`getMetrics()` returns a map for monitoring: `name`, `closed`, `healthy`,
`usingVirtualThreads`, `ownsExecutor`, `poolSize`, `inFlightCount`, `totalSubmitted`,
`timeoutCount`, `admissionControlEnabled`, and `admissionPermitsAvailable` when a limit is
set. For a platform `ThreadPoolExecutor` it adds the executor's own counters (`activeCount`,
`queueSize`, `completedTaskCount` and the pool-size figures). `isHealthy()` is `true` while the
pool is open and any executor it owns is still running.

Problems found while setting up the shared executors are kept in a bounded static list, read
with `ConcurrentPool.getErrors()` and `hasErrors()`.

== Building Pools: `ExecutorPoolFactory`

`ExecutorPoolFactory` creates pools without the caller naming `ConcurrentPool`, which keeps
client code coupled to the interface only.

[source,groovy]
----
ExecutorPool pool = ExecutorPoolFactory.wrap(existingExecutor)

ExecutorPool named = ExecutorPoolFactory.builder()
        .name('ingest')
        .executor(existingExecutor)      // optional; omit for the virtual-thread default
        .scheduler(existingScheduler)    // optional; omit for the shared scheduler
        .build()
----

Executors supplied through the factory are never owned by the resulting pool.

== Choosing a Pool

* Use the default pool for work that mostly waits: I/O, remote calls, anything that blocks.
  Virtual threads are made for it and there is nothing to size.
* Use a fixed platform pool for CPU-bound work, where the useful degree of parallelism is the
  number of cores.
* Add `withMaxInFlight` when the work reaches a resource with its own limit, such as a
  database or a rate-limited API.
* Pass a pool in explicitly when a test needs to control execution, or when several components
  should share one limit.
